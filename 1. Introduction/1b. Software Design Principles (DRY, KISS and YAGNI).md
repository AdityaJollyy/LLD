# Software Design Principles

Software design principles are **guidelines that help developers create software systems that are easy to understand, maintain, and extend**.

These principles can be applied at both **High-Level Design (HLD)** and **Low-Level Design (LLD)** stages.

The three cornerstone software design principles covered here are:

* **DRY — Don't Repeat Yourself**
* **KISS — Keep It Simple, Stupid**
* **YAGNI — You Aren't Gonna Need It**

<details>
<summary><strong>🔄 1. DRY — Don't Repeat Yourself</strong></summary>

### Definition

**DRY (Don't Repeat Yourself)** states that:

> Every piece of knowledge should have a **single, unambiguous, authoritative representation** within a system.

In simple terms, **avoid unnecessary duplication of code or logic**.

When the same logic is repeated in multiple places, maintaining the system becomes harder and more error-prone. If the logic needs to change, every occurrence must be updated, and it is easy to miss one.

### Importance of DRY

Following DRY provides:

* **Reduced redundancy** — avoids unnecessary duplication.
* **Easier maintenance** — changes can be made in one place.
* **Single point of change** — common logic has one authoritative implementation.

### Example

Suppose two methods, `printArea1()` and `printArea2()`, contain the same logic for calculating an area.

This violates DRY because the area-calculation logic exists in multiple places.

If the calculation needs to change, we must modify it in both methods. Forgetting one occurrence can introduce inconsistent behavior.

A better approach is to extract the common logic into a single reusable method:

```java
calculateArea()
```

Now both methods can use `calculateArea()`.

The calculation exists in **one place**, so any future change only needs to be made there.

### Applying DRY in Practice

DRY can be applied by:

* Identifying repetitive code and replacing it with a **single reusable code segment**.
* Extracting common functionality into **methods or utility classes**.
* Leveraging existing **libraries and frameworks** when they provide the required functionality.
* Regularly refactoring duplicate logic across **classes or layers** as the codebase grows.

> **Personal Note — Don't Reinvent the Wheel:**
> When an existing library, framework, or service already provides a reliable solution, use it instead of building everything yourself.
>
> For example, a SaaS owner generally has little reason to build a **payment gateway from scratch** when established payment solutions already exist. The development effort is better spent on the actual product and its important functionality.

### Refactor Regularly

As a system grows, its codebase will naturally become larger. Repetition that was not significant initially can become substantial as more features and classes are added.

Therefore, **identify and refactor meaningful duplication periodically** rather than allowing duplicated logic to spread throughout the system.

However, this does **not** mean every small repetition should immediately be abstracted.

---

### When NOT to Use DRY

DRY should not be applied blindly. Sometimes keeping code separate is better than forcing it into a shared abstraction.

#### 1. Premature Abstraction

Do not extract common code too early.

Two pieces of code may look identical today but may need to evolve differently later. Combining them prematurely can create **unnecessary coupling between unrelated parts**.

**Example:**

Suppose `AdminReport` and `UserReport` currently have identical `generateReport()` logic.

If they are likely to develop different formatting or validation rules later, combining them into one shared method can make future changes harder.

**Key idea:**

> Don't abstract code merely because it looks similar. Make sure the shared abstraction represents genuinely common behavior.

---

#### 2. Performance-Critical Code

DRY should not be applied to performance-sensitive code if the resulting abstraction causes inefficiency.

Sometimes repeating a small piece of optimized low-level logic can be preferable to introducing:

* Additional function calls
* Indirection
* Generic wrappers

These abstractions can reduce performance or prevent certain compiler optimizations such as **inlining**.

**Example:**

In a game engine, a small arithmetic calculation may be written directly inside a frequently executed loop instead of calling a generic helper function every iteration.

Although this introduces some repetition, avoiding the abstraction may keep the **hot path more optimized**.

---

#### 3. Sacrificing Readability

Do not apply DRY if extracting repeated code makes the code **harder to understand**.

For example, if a function calls many tiny helper functions for very small operations, understanding the main logic may require repeatedly jumping between different functions.

In such a case, keeping a small operation directly at the point where it is used can make the code **clearer and easier to follow**.

> **Clarity should take priority over DRY when an abstraction makes simple logic harder to understand.**

---

#### 4. Very Small Repetition

Not every tiny repetition needs to be abstracted immediately.

Creating separate methods, classes, or utilities for extremely small pieces of repeated code can itself make the codebase difficult to navigate and maintain.

It is often better to wait until there is **significant and meaningful repetition** before introducing an abstraction.

---

#### 5. Legacy Codebases

Be particularly careful when applying DRY to **existing legacy code**.

Legacy systems may have:

* Limited or no automated tests.
* Incomplete documentation.
* Existing behavior that users depend on.

Extracting apparently similar code into a shared method can unintentionally change subtle behavior and introduce bugs or downtime.

A safer approach is often:

> **Leave working legacy code alone unless there is a reason to modify it.**

If the functionality must be changed, refactoring can then be performed carefully with appropriate testing.

**Example:**

Suppose an old payment system has similar validation logic in several places but has no automated tests.

Combining the validation code into a single method might unintentionally change behavior that existing users depend on.

Therefore, it is safer not to refactor it merely for the sake of DRY. If the functionality needs modification, it can be refactored carefully as part of that change.

<summary><strong>✨ 2. KISS — Keep It Simple, Stupid</strong></summary>

### Definition

**KISS (Keep It Simple, Stupid)** states that **simplicity should be a key goal in software design and unnecessary complexity should be avoided**.

In simple terms:

> **Use the simplest possible solution that works.**

Avoid writing clever or unnecessarily complicated code when a straightforward solution is sufficient.

### Importance of KISS

Following KISS provides:

* **Easier debugging**
* **Improved readability**
* **Better maintainability**
* **Faster development**

### Example

Suppose we need to determine whether a number is **even or odd**.

A complicated implementation might:

* Introduce unnecessary variables.
* Use extra `if-else` logic.
* Make the code longer.
* Make the logic harder to follow.

A simple implementation can express the same logic much more directly.

For example:

```java
return number % 2 == 0;
```

This is preferable because it is:

* **Simple**
* **Easy to read**
* **Easy to understand**
* Free from unnecessary overengineering

### Key Idea

> **If a simple solution solves the problem effectively, there is usually no reason to replace it with a more complicated one.**

<summary><strong>🚫 3. YAGNI — You Aren't Gonna Need It</strong></summary>

### Definition

**YAGNI (You Aren't Gonna Need It)** means:

> **Implement things when you actually need them, not when you merely think you might need them in the future.**

In simple terms, **do not add functionality until it is actually necessary**.

Avoid building features based only on speculation about possible future requirements.

This keeps the codebase cleaner and reduces unnecessary complexity.

### Example

Suppose you are asked to build a **note-taking application** that currently needs only:

* Creating notes
* Viewing notes

While developing it, you start thinking:

> "What if users later want categories? What if they need tags? What if they want Google Drive synchronization?"

Building all of these features in advance creates:

* Unnecessary complexity
* Additional development work
* Wasted time

If those requirements actually arise later, they can be implemented when they are needed.

### Importance of YAGNI

Following YAGNI provides:

* **Reduced waste**
* **A simpler codebase**
* **Faster development**

---

### When NOT to Use YAGNI

YAGNI should also not be applied blindly. There are situations where preparing for a known or important future requirement can be beneficial.

#### 1. When Requirements Are Well-Known

If a feature is **guaranteed and will be implemented soon**, designing for it now may avoid unnecessary refactoring.

**Example:**

Suppose a messaging service currently supports only text messages, but the product team has already committed to adding **image support in two sprints**.

Designing the data model to accommodate attachments now may save significant refactoring later.

The key distinction is that this is a **known and committed requirement**, rather than a feature that is merely being imagined.

---

#### 2. Performance-Critical Areas

In systems where **performance is a first-class concern**, strictly avoiding all future preparation can sometimes be counterproductive.

Preemptively building and testing realistic usage patterns can help identify performance bottlenecks before they become difficult to address.

**Simple Example:**

Suppose an application is expected to process a very large number of requests through a particular component.

Even if the current workload is small, designing and testing that critical component with realistic high-load patterns may reveal performance bottlenecks early.

This can justify some preparation beyond the immediate minimum requirement when performance is a major concern.

<summary><strong>⚖️ 4. DRY vs KISS vs YAGNI</strong></summary>


| **Principle** | **Core Idea**                       | **Main Goal**                                |
| ------------- | ----------------------------------- | -------------------------------------------- |
| **DRY**       | Avoid unnecessary duplication       | Reduce redundancy and simplify maintenance   |
| **KISS**      | Prefer simple solutions             | Avoid unnecessary complexity                 |
| **YAGNI**     | Build only what is currently needed | Avoid unnecessary features and wasted effort |

### In Simple Words

* **DRY → Don't repeat the same knowledge or logic unnecessarily.**
* **KISS → Don't make a simple problem unnecessarily complicated.**
* **YAGNI → Don't build something just because you might need it someday.**

<summary><strong>🎯 5. Interview Quick Revision</strong></summary>

### What is DRY?

**DRY (Don't Repeat Yourself)** states that every piece of knowledge should have a single, unambiguous, authoritative representation within a system. It helps reduce duplication and makes changes easier to maintain.

**Important:** DRY should not be applied blindly. Avoid premature abstraction, unnecessary abstraction of tiny code, performance-impacting abstractions, readability sacrifices, and risky refactoring of stable legacy code.

---

### What is KISS?

**KISS (Keep It Simple, Stupid)** means that simplicity should be a key goal of software design. Use the **simplest solution that effectively solves the problem** and avoid unnecessary complexity.

---

### What is YAGNI?

**YAGNI (You Aren't Gonna Need It)** means that functionality should be implemented **when it is actually needed**, rather than being built based on speculation about future requirements.

---

### Quick Memory Trick

> **DRY → Don't Repeat**
> **KISS → Keep It Simple**
> **YAGNI → Don't Build Yet**

Together, these principles encourage software that avoids **unnecessary duplication, unnecessary complexity, and unnecessary functionality**.
