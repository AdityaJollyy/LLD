# Single Responsibility Principle (SRP)

<details>
<summary><strong>📌 1. Introduction to SOLID Principles</strong></summary>

**SOLID** is a set of **five principles** for writing clean, scalable, and maintainable **object-oriented code**.

The **S** in SOLID stands for the **Single Responsibility Principle (SRP)**.

</details>

<details>
<summary><strong>📖 2. Definition of Single Responsibility Principle</strong></summary>

The **Single Responsibility Principle (SRP)** states:

> **A class should have only one reason to change.**

In other words, a class should have:

* **One job**
* **One responsibility**
* **One purpose**

A class that handles multiple responsibilities becomes **coupled**.

This means that when one responsibility changes, other responsibilities handled by the same class may also be affected. This can create a **ripple effect of changes throughout the codebase**.

### Key Idea

> **One class → One responsibility → One reason to change**

SRP is therefore about keeping responsibilities separated so that changes in one area do not unnecessarily affect other areas.

</details>

<details>
<summary><strong>👨‍🍳 3. Real-Life Analogy</strong></summary>

Consider a chef who is responsible for:

* Cooking food
* Cleaning
* Serving food
* Ordering groceries

If the chef is busy cleaning, they cannot focus completely on cooking, which may affect the quality of the food.

Instead, each task can be assigned to a different person:

| **Person**  | **Responsibility** |
| ----------- | ------------------ |
| **Chef**    | Cooking            |
| **Cleaner** | Cleaning           |
| **Waiter**  | Serving            |
| **Manager** | Ordering groceries |

Now each person can focus on their **specific responsibility**.

Similarly, in software, instead of putting multiple unrelated responsibilities into one class, they should be separated into focused components.

</details>

<details>
<summary><strong>💻 4. SRP Example — Online Compiler</strong></summary>

Consider an online compiler system.

The compiler currently performs several different tasks:

1. Adds driver code.
2. Performs syntax checks.
3. Runs code using already-provided test cases.
4. Stores the output in a database.
5. Returns the required output to the user.

Putting all these responsibilities into a single `Compiler` class would violate **SRP** because the class would have multiple reasons to change.

### Applying SRP

Instead, we can divide these responsibilities into separate classes:

| **Class**             | **Responsibility**            |
| --------------------- | ----------------------------- |
| `DriverCodeGenerator` | Adds driver code              |
| `SyntaxChecker`       | Performs syntax checks        |
| `TestRunner`          | Runs code with test cases     |
| `DatabaseManager`     | Stores output in the database |
| `UserOutputHandler`   | Returns output to the user    |

A separate `Coordinator` class can coordinate the interaction between these classes/modules.

### Result

Each class now has a **focused responsibility**.

For example:

* If syntax-checking logic changes → modify `SyntaxChecker`.
* If database-related logic changes → modify `DatabaseManager`.
* If output handling changes → modify `UserOutputHandler`.

The other components do not need to be unnecessarily affected.

### Benefits of This Design

Following SRP makes the system:

* **More modular**
* **Easier to maintain**
* **Less prone to bugs**
* Easier to modify or replace individual components independently

</details>

<details>
<summary><strong>⭐ 5. Advantages of SRP</strong></summary>

### 5.1 Improved Maintainability

Changes in one part of the system are less likely to affect unrelated parts.

This makes the code easier to:

* Maintain
* Update
* Modify

---

### 5.2 Enhanced Readability

Smaller, focused classes are easier to:

* Read
* Understand
* Navigate

Each class has a clear purpose, making its behavior easier to comprehend.

---

### 5.3 Better Reusability

Classes with a **single responsibility** can be reused in different contexts without bringing unnecessary dependencies or unrelated functionality with them.

---

### 5.4 Facilitates Testing

Smaller classes are generally easier to test because they have:

* Fewer responsibilities
* Fewer dependencies

Each responsibility can therefore be tested more independently.

---

### 5.5 Lower Risk in Changes

Since each class handles only one concern, modifying it is less likely to introduce **unintended side effects** in other parts of the system.

</details>

<details>
<summary><strong>⚠️ 6. Common Mistakes When Violating SRP</strong></summary>

### 6.1 Mixing Database Logic with Business Logic

A common mistake is putting both:

* **Data-access logic**, such as SQL or JDBC
* **Core business rules**

inside the same class.

This makes it difficult to change the database-related layer without also affecting the business logic.

---

### 6.2 Coupling UI Code with Business Logic

Another common mistake is embedding application/business logic directly inside the **UI layer**.

This makes it difficult and tedious to change the UI without affecting the underlying application logic.

### Core Problem

In both cases, unrelated responsibilities become tightly connected, making changes more difficult and increasing the possibility of unintended effects.

</details>

<details>
<summary><strong>🧩 7. SRP Is Not Just for Classes</strong></summary>

An important question is:

> **Is SRP only applicable to classes?**

**No.**

The principle can be applied at different levels of a software system, including:

* **Methods**
* **Classes**
* **Modules**
* **Microservices**
* **Entire systems**

The key idea remains the same:

> **Each component should have a single responsibility, and changes in one area should not unnecessarily affect other areas.**

Therefore, SRP is not merely a rule for classes. It is a **design mindset** that can be applied from the **smallest method to the largest system design**.

</details>

<details>
<summary><strong>🎯 8. Interview Quick Revision</strong></summary>

### What is SRP?

**Single Responsibility Principle (SRP)** states that **a class should have only one reason to change**. In simple terms, a class should have one job, one responsibility, and one purpose.

### Why is SRP important?

It helps achieve:

* **Better maintainability**
* **Improved readability**
* **Better reusability**
* **Easier testing**
* **Lower risk of unintended side effects**

### What happens when SRP is violated?

When a component has multiple responsibilities, those responsibilities become **coupled**. A change in one responsibility can then cause a **ripple effect** across other parts of the codebase.

### Is SRP only for classes?

**No.** SRP can be applied to **methods, classes, modules, microservices, and entire systems**.

### One-Line Memory Trick

> **SRP → One component should have one responsibility and one reason to change.**

</details>
