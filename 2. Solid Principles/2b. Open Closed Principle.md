# Open/Closed Principle (OCP)

<details>
<summary><strong>📌 1. Introduction to SOLID Principles</strong></summary>

**SOLID** is a set of **five principles** for writing clean, scalable, and maintainable **object-oriented code**.

The **O** in SOLID stands for the **Open/Closed Principle (OCP)**.

</details>

<details>
<summary><strong>📖 2. Definition of Open/Closed Principle</strong></summary>

The **Open/Closed Principle (OCP)** states:

> **Software entities such as classes, modules, and functions should be open for extension, but closed for modification.**

This means that the **behavior of an existing module should be extendable without modifying its existing source code**.

The goal is to reduce the risk of **breaking existing functionality** when requirements change.

### In Simple Terms

Instead of modifying stable, existing code every time a new requirement appears:

> **Extend the existing behavior without changing the existing implementation.**

</details>

<details>
<summary><strong>🔌 3. Real-Life Analogy — Power Adapter</strong></summary>

Imagine travelling from **India to the UK**.

Your Indian charger may not directly fit into a UK power socket. Instead of modifying or replacing the charger, you can use a **travel adapter**.

The adapter:

* **Extends** the usability of your existing charger.
* Allows the charger to work with the new socket.
* Does **not modify the charger itself**.

This is similar to OCP in software design.

Instead of modifying existing, stable code whenever new functionality is required, we **extend the system with new implementations**.

> **OCP → Extend existing behavior without modifying the existing stable implementation.**

</details>

<details>
<summary><strong>💰 4. Real-World Example — Region-Based Tax Calculation</strong></summary>

Consider an **invoicing system** that needs to calculate taxes for different regions.

For this example, assume:

| **Region** |        **Tax** |
| ---------- | -------------: |
| **India**  |      GST — 18% |
| **US**     | Sales Tax — 8% |
| **UK**     |      VAT — 12% |

As the invoicing system grows, more regions may need to be supported, such as Germany.

The design of the tax calculation system determines whether adding a new region requires modifying existing code or simply extending it.

</details>

<details>
<summary><strong>❌ 5. Bad Design — Violating OCP</strong></summary>

A common approach is to put all regional tax calculations inside a single method:

### Code

```java
class Invoice {

    public double calculateTax(String region, double amount) {

        if (region.equals("India")) {
            return amount * 0.18;
        } 
        else if (region.equals("US")) {
            return amount * 0.08;
        } 
        else if (region.equals("UK")) {
            return amount * 0.12;
        }

        return 0;
    }
}
```

### Why Does This Violate OCP?

If a new region such as **Germany** needs to be supported, we must modify the existing method:

```java
else if (region.equals("Germany")) {
    return amount * 0.15;
}
```

This creates several problems:

* Adding a new region requires **modifying existing code**.
* Existing logic could accidentally be broken while adding new functionality.
* The code becomes harder to **test**.
* The code becomes harder to **maintain**.
* Supporting more regions makes the conditional logic increasingly difficult to **scale**.
* It violates the **Open/Closed Principle**.

</details>

<details>
<summary><strong>✅ 6. Good Design — Following OCP</strong></summary>

Instead of putting all tax calculations inside `Invoice`, we can create a common interface and separate tax calculations into region-specific implementations.

### Step 1 — Define the Tax Strategy Interface

```java
interface TaxCalculator {
    double calculateTax(double amount);
}
```

The `TaxCalculator` interface defines a **common contract** that every region-specific tax calculator must follow.

This enables different tax implementations to be used through the same interface.

---

### Step 2 — Implement Region-Specific Tax Calculators

```java
class IndiaTaxCalculator implements TaxCalculator {

    public double calculateTax(double amount) {
        return amount * 0.18; // GST
    }
}

class USTaxCalculator implements TaxCalculator {

    public double calculateTax(double amount) {
        return amount * 0.08; // Sales Tax
    }
}

class UKTaxCalculator implements TaxCalculator {

    public double calculateTax(double amount) {
        return amount * 0.12; // VAT
    }
}
```

Each class provides a **concrete implementation** of the `TaxCalculator` interface.

Each class encapsulates the tax logic for its respective region.

---

### Step 3 — Use Dependency Injection in `Invoice`

```java
class Invoice {

    private TaxCalculator taxCalculator;

    public Invoice(TaxCalculator taxCalculator) {
        this.taxCalculator = taxCalculator;
    }

    public double calculateTax(double amount) {
        return taxCalculator.calculateTax(amount);
    }
}
```

The `Invoice` class does not directly depend on a specific tax type.

Instead, it receives a `TaxCalculator` from outside.

This is called **Dependency Injection**.

Therefore, `Invoice` is decoupled from specific tax implementations.

---

### Step 4 — Main Running Code

```java
public class Main {

    public static void main(String[] args) {

        TaxCalculator taxCalculator = new IndiaTaxCalculator();

        Invoice invoice = new Invoice(taxCalculator);

        double tax = invoice.calculateTax(1000);

        System.out.println("Tax: " + tax);
    }
}
```

In the `main` method:

1. We create the appropriate tax calculator.
2. We pass it to the `Invoice` object.
3. `Invoice` uses the injected `TaxCalculator` to calculate the tax.

This makes the system easily **extensible** for new regions.

---

### Step 5 — Adding Germany

Suppose Germany needs to be supported with a **15% tax**.

We simply create another implementation:

```java
class GermanyTaxCalculator implements TaxCalculator {

    public double calculateTax(double amount) {
        return amount * 0.15;
    }
}
```

Then we can pass it to `Invoice`:

```java
TaxCalculator taxCalculator = new GermanyTaxCalculator();

Invoice invoice = new Invoice(taxCalculator);
```

### What Did We Avoid Modifying?

We did **not** need to modify:

* `TaxCalculator`
* `Invoice`
* `IndiaTaxCalculator`
* `USTaxCalculator`
* `UKTaxCalculator`

We simply **added a new implementation**.

This is the core idea of OCP:

> **New behavior is added through extension rather than by modifying existing stable code.**

</details>

<details>
<summary><strong>🧩 7. Complete Code — Good Design</strong></summary>

This is the **complete OCP implementation** in one place for quick revision:

```java
// Tax strategy interface
interface TaxCalculator {
    double calculateTax(double amount);
}

// Region-specific tax calculators
class IndiaTaxCalculator implements TaxCalculator {

    public double calculateTax(double amount) {
        return amount * 0.18; // GST
    }
}

class USTaxCalculator implements TaxCalculator {

    public double calculateTax(double amount) {
        return amount * 0.08; // Sales Tax
    }
}

class UKTaxCalculator implements TaxCalculator {

    public double calculateTax(double amount) {
        return amount * 0.12; // VAT
}

// Germany can be added without modifying existing classes
class GermanyTaxCalculator implements TaxCalculator {

    public double calculateTax(double amount) {
        return amount * 0.15; // Tax
    }
}

// Invoice depends on the abstraction, not a specific tax type
class Invoice {

    private TaxCalculator taxCalculator;

    // Dependency Injection
    public Invoice(TaxCalculator taxCalculator) {
        this.taxCalculator = taxCalculator;
    }

    public double calculateTax(double amount) {
        return taxCalculator.calculateTax(amount);
    }
}

// Main running code
public class Main {

    public static void main(String[] args) {

        // Select the required tax calculator
        TaxCalculator taxCalculator =
                new IndiaTaxCalculator();

        // Inject the selected calculator into Invoice
        Invoice invoice = new Invoice(taxCalculator);

        // Calculate tax
        double tax = invoice.calculateTax(1000);

        System.out.println("Tax: " + tax);
    }
}
```

### How to Read This Code

The design can be understood in this order:

```text
TaxCalculator
      │
      ├── IndiaTaxCalculator
      ├── USTaxCalculator
      ├── UKTaxCalculator
      └── GermanyTaxCalculator
                  │
                  ▼
               Invoice
                  │
                  ▼
            calculateTax()
```

**Key relationships:**

* `TaxCalculator` → defines the common contract.
* Region-specific calculators → provide their own tax implementations.
* `Invoice` → depends only on `TaxCalculator`.
* `Main` → decides which tax calculator to create and inject.
* New region → add a new implementation.

### Why Is This OCP-Compliant?

Suppose we add France tomorrow.

We only need:

```java
class FranceTaxCalculator implements TaxCalculator {

    public double calculateTax(double amount) {
        return amount * 0.20;
    }
}
```

Then:

```java
TaxCalculator taxCalculator =
        new FranceTaxCalculator();

Invoice invoice = new Invoice(taxCalculator);
```

The existing `Invoice` class remains unchanged.

</details>

<details>
<summary><strong>⚙️ 8. How the Good Design Works</strong></summary>

### 8.1 Tax Strategy Interface

The `TaxCalculator` interface provides a **common contract** for all regional tax calculators.

It enables:

* A common structure for tax calculators.
* **Polymorphism**
* Easy addition of new regional implementations.

### 8.2 Region-Specific Implementations

Classes such as:

* `IndiaTaxCalculator`
* `USTaxCalculator`
* `UKTaxCalculator`
* `GermanyTaxCalculator`

encapsulate their respective tax logic.

Each new region can therefore be introduced as a separate implementation.

### 8.3 Dependency Injection

`Invoice` receives a `TaxCalculator` from outside rather than creating or depending directly on a specific tax calculator.

This **decouples `Invoice` from specific tax types**.

The `main` code can choose the appropriate implementation and inject it into `Invoice`.

### Overall Flow

```text
                    TaxCalculator
                         │
        ┌────────────────┼────────────────┐
        │                │                │
        ▼                ▼                ▼
 IndiaTaxCalculator  USTaxCalculator  UKTaxCalculator
        │                │                │
        └────────────────┼────────────────┘
                         │
                         │
                         ▼
                      Invoice
                         │
                         ▼
                  calculateTax()
```

The important point is that `Invoice` works with the **`TaxCalculator` interface**, rather than directly depending on a specific regional implementation.

</details>

<details>
<summary><strong>🎯 9. When to Apply OCP</strong></summary>

The Open/Closed Principle is especially useful in the following situations:

### 9.1 When a Module Is Expected to Change

Apply OCP when a module is expected to evolve because of changing:

* Business requirements
* Technical requirements

If new behavior is likely to be added, designing the module for extension can make those changes safer.

### 9.2 When Functionality Needs to Be Extended

OCP is useful when new functionality needs to be added **without modifying existing, tested code**.

This helps protect existing behavior from unnecessary changes.

### 9.3 Frameworks, Plugins, and Extensible Systems

OCP is especially useful when building systems designed to support different implementations or extensions, such as:

* **Billing engines**
* **Tax calculators**
* **UI components**
* **Frameworks**
* **Plugins**

These systems naturally need to support new behavior over time.

### 9.4 Protecting Stable Production Code

OCP can help safeguard **stable, production-ready modules** from regressions caused by directly modifying existing code.

Instead of repeatedly changing stable functionality, new behavior can be introduced through extensions.

### 9.5 When a Class Becomes a God Class

If a class starts handling too many responsibilities or contains extensive branching logic, it may be becoming a **God Class**.

This can be a signal that behaviors should be extracted into separate, extendable components.

For example, instead of continuously adding more regional conditions to one tax-calculation class, separate tax implementations can be created.

### ⚠️ Important Consideration

OCP should **not be applied preemptively** without a clear need for extension.

Adding abstractions before there is an actual extension requirement can introduce:

* Unnecessary abstraction
* Additional complexity

OCP is generally most effective when applied in response to:

* **Observed patterns of change**, or
* A **well-understood need for scalability**

</details>

<details>
<summary><strong>❌ 10. Common Misconceptions About OCP</strong></summary>

### 10.1 "Open/Closed Means Code Should Never Be Changed Again"

This is an incorrect interpretation of OCP.

OCP does not mean that existing code can **never** be changed.

Instead, it emphasizes **avoiding unnecessary modification of core, stable logic** while allowing behavior to be **safely extended**.

---

### 10.2 "OCP Leads to Too Many Classes, So It's Overkill"

Applying OCP can result in additional:

* Classes
* Interfaces
* Abstractions

However, this can improve:

* **Modularity**
* **Testability**
* **Maintainability**

This trade-off can be particularly useful in systems that are expected to evolve.

---

### 10.3 "OCP Makes Code Harder to Read"

In small or short-lived projects, additional abstraction can sometimes feel unnecessary.

However, in systems with:

* Complex behavior
* Frequent changes

well-structured extensibility can actually improve clarity by:

* Separating concerns.
* Reducing conditional logic.

---

### 10.4 "OCP Should Always Be Applied Upfront"

OCP should not automatically be applied everywhere from the beginning.

Applying it preemptively can lead to:

* Unnecessary abstractions
* Increased complexity

It is often more effective to apply OCP when there is an **emerging pattern of change** that justifies the abstraction.

---

### 10.5 "Refactoring Contradicts OCP"

Refactoring does **not** violate OCP.

In fact, refactoring can be a step toward making code **more compliant with OCP** by improving:

* Structure
* Extensibility

For example, refactoring a large conditional-based tax calculator into a set of region-specific implementations can make it easier to add new regions without modifying existing logic.

---

### 10.6 "OCP Makes Retesting Legacy Code Unnecessary"

OCP aims to reduce the need to modify and retest stable components.

However, **new extensions still require thorough testing**.

When a new implementation is added, it must be tested to ensure:

* It behaves correctly.
* It integrates correctly with the existing system.

OCP reduces unnecessary modification of stable components, but it does **not eliminate the need for testing new functionality**.

</details>

<details>
<summary><strong>⚖️ 11. Bad Design vs Good Design</strong></summary>

| **Aspect**              | **Without OCP**                                 | **With OCP**                                |
| ----------------------- | ----------------------------------------------- | ------------------------------------------- |
| **Adding a new region** | Modify existing conditional logic               | Add a new implementation                    |
| **Existing code**       | Frequently modified                             | Kept stable where possible                  |
| **Tax logic**           | Centralized in one conditional structure        | Separated into region-specific classes      |
| **Coupling**            | Higher                                          | Lower                                       |
| **Extensibility**       | Difficult                                       | Easier                                      |
| **Testing**             | Existing logic may need retesting after changes | New extensions can be tested separately     |
| **Scalability**         | Becomes harder as regions increase              | New regions can be added through extensions |

</details>

<summary><strong>🎯 12. Interview Quick Revision</strong></summary>

### What is OCP?

**Open/Closed Principle states that software entities such as classes, modules, and functions should be open for extension but closed for modification.**

### What does "open for extension" mean?

New behavior can be added to the system without changing the existing implementation.

### What does "closed for modification" mean?

Existing, stable code should not need to be modified every time new functionality is introduced.

### When should OCP be applied?

OCP is especially useful when:

* A module is expected to evolve.
* New functionality needs to be added without changing tested code.
* Building extensible systems such as plugins, frameworks, billing engines, tax calculators, or UI components.
* Protecting stable production code from regressions.
* A class is becoming a **God Class** with excessive branching logic.

### Important Caution

> **Do not apply OCP blindly or preemptively.**

If there is no clear extension requirement, introducing abstractions can create unnecessary complexity.

OCP is most useful when there is an **observed pattern of change or a clear need for extensibility**.

### One-Line Memory Trick

> **OCP → Extend existing behavior without unnecessarily modifying stable existing code.**

</details>
